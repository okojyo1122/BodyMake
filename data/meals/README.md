# 献立データの仕様（data/meals）

画面（`meals/`）とデータを分離しています。献立の追加・更新（手動・将来のAI生成）は、このフォルダのJSONを編集し、`npm run validate` が通ることを確認してから公開します。

**APIキーなどの秘密情報は、このフォルダ・HTML・JavaScriptに絶対に置かないでください。**GitHub Pagesは公開サイトです。

## ファイル

| ファイル | 内容 |
|---|---|
| `config.json` | 確定条件：人数、週の予算、米の扱い、除外アレルゲン、個別設定の初期値と範囲、夫婦それぞれの固定朝食、同じ料理の再登場ルール |
| `ingredients.json` | 食材マスタ：カテゴリ、基本単位と単位変換、購入単位と推定価格、価格状態、栄養（目安）、加工食品かどうか、アレルゲン情報 |
| `index.json` | 週の一覧（`current` は表示する週）。過去週も残し、同じ料理の連続チェックに使います |
| `weeks/YYYY-MM-DD.json` | 1週間分の献立（月曜始まり）。料理（レシピ）はこのファイルの中で完結させます |

## 数量の考え方

- **レシピの使用量**：`{ "id": "chicken_breast", "qty": 200, "unit": "g", "main": true }`。単位は食材の基本単位（`unit`）か、`conversions` にある単位（大さじ・小さじ・少々など）を使います。
- **2人分**：昼食・夕食のレシピは「主菜倍率1.0の2人分」で書きます。`main: true` の食材だけが主菜倍率で増減します。
- **ご飯**：昼食・夕食のご飯はレシピに書かず、食事の `withRice: true` と個別設定（本人・妻のg数）から計算します。米は `excludedFromBudget: true` で予算対象外です。
- **販売単位**：`purchase.size`（基本単位での1個あたりの量）と `purchase.label`（例：1パック（約300g））。
- **購入数量**：必要量の合計 ÷ `purchase.size` を切り上げます（例：800g ÷ 300g → 3パック）。
- **購入価格**：購入数量 × `purchase.priceYen`。
- **価格状態**：`purchase.priceStatus` は `estimated`（推定）か `unset`（未設定）のどちらかです。未設定の食材がある場合、合計は「未確定」として扱い、予算内とは表示しません。

## 常備品と週の在庫

- `staple: true` は常備品（調味料・ジャムなど、週をまたいで使うもの）。加工品（`processed: true`）にだけ付けられます（生鮮食品に付けると検証エラー）。
- **初回購入費用**：常備品も含めて全食材を購入する場合。**通常週の費用**：常備品は在庫あり、それ以外は購入する場合。どちらも購入単位で計算し、在庫チェックの状態には左右されません。価格未設定があれば両方とも「未確定」です。
- 週の状態（LocalStorage `bodymake.meals.v1.week.<週>`）が未保存の週を初めて表示したとき、直前の保存済みの週から**常備品の「在庫あり」だけ**を引き継ぎ、すぐ保存します。以後は引き継ぎで上書きしません。生鮮食品の在庫と「購入済み」は引き継ぎません。

## アレルギー（えび・かに）

- 食材ごとに `containsAllergens`（例：`["shrimp"]`）と `allergenStatus` を必ず設定します。
  - `free`：加工されていない単一の食材（肉・野菜・卵など）にだけ使えます。
  - `needs_label_check`：加工食品・調味料・だしなど。商品によって原材料が違うため、購入前に確認する対象として表示します。
  - `contains`：除外アレルゲンを含みます（検証エラーになります）。
- `processed: true` の食材を `free` にすると、検証エラーになります。
- `needs_label_check` の食材には `labelCheckReason`（確認が必要な理由）と `labelCheckRisk`（`high` / `medium` / `low`）が必須です。確認優先度は原材料確認の必要性の目安で、危険性を断定するものではありません。
- 判定は3段階です：**アレルゲン検出**（検証エラー）／**判定が曖昧**（要確認の警告。画面上部に表示）／**登録データ上で検出なし**（安全の保証ではありません）。
- 判定前に表記ゆれを正規化します（NFKC で全角・半角を統一、英字を小文字化、ひらがな・カタカナの両方で照合）。キーワードは `config.json` の `allergens.excluded[].keywords` と `sharedKeywords`。
- 欄ごとの扱い（`allergens.fieldModes`）：
  - 食材名・原材料情報（`strict`）：副詞の除外を一切しません。「やわらかに」のような形でもエラーです（変更すると検証エラー）。
  - 料理名（`name`）：明確な副詞（`adverbWhitelist`）は要確認の警告、それ以外はエラー。
  - 調理手順（`prose`）：明確な副詞は検出なし、`ambiguousPatterns`（未登録の「〜やかに／〜らかに」、ひらがなの「たらば」など）は要確認の警告、それ以外はエラー。副詞の除外はひらがな表記にだけ適用し、カタカナ「カニ」・漢字「蟹」は常にエラーです。
- 名前に含まれていないことを安全の根拠にはしません。加工食品は実際の商品パッケージの原材料表示と混入の注意表示を確認してください。

## 検証

```
npm test               # ロジックとデータのテスト
npm run validate       # 全週を検証（エラーがあれば終了コード1）
node scripts/validate.mjs --file 候補.json   # 未登録の週（更新候補）を検証
```

主なエラー条件：構造の不備、存在しない食材や料理、変換できない単位、月曜始まりでない週、日付のずれ、えび・かにを含む食材、原材料確認の理由・優先度の欠落、直近 `rules.noRepeatWeeks` 週と同じ主菜、通常週の費用（常備品は在庫あり）でも予算を超える場合。
